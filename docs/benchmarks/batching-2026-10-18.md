# Batched windows, 2026-10-18

The backtest now sends every window of a series to a foundation model in one call
(`forecast_batch`). Contexts of different lengths are left-padded: Timestral masks NaN
padding, and the Chronos-2 pipeline pads ragged lists itself. Weights load once per
checkpoint and device per process, before the clock starts.

## Same forecasts

Finance suite, 6 windows, all Timestral sizes and both Chronos-2 sizes (462 rows), before
against after:

| score | max abs difference |
|---|---|
| MASE | 6.6e-05 |
| WQL | 5.7e-07 |
| coverage_80 | 0 |
| direction | 0 |

Per forecast, batched against one-at-a-time on Brent (contexts up to 9,108 points), the
largest relative difference is 1.5e-06. That is float32 kernel-ordering noise.
`tests/test_batching.py -m weights` guards it at 1e-3 absolute.

## Reading it

- **Many more windows are now cheap.** Rerunning the benchmarks with 24–48 windows
  costs seconds, not minutes, which addresses the thin samples flagged in every report so
  far.
- **What's left of the 17 s is fixed overhead:** Python, torch and CUDA start-up, data
  loading, and one weight load per model. The forecasting itself is about 6 s
  (per-window `seconds` × 66 windows, summed over the six models).
- **The earlier reports' `seconds` columns were dominated by load time.** Each now has a
  dated correction note. Their accuracy figures stand.
- **Timestral-5M** is slower per window than 28M after batching (0.034 s against
  0.009 s), which the warm Brent microbenchmark doesn't reproduce (0.08 s against
  0.06 s for 12 windows). The cause hasn't been investigated; it may be warm-up order,
  since 5M is the first foundation model each run.
